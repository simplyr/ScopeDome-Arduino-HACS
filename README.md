# ScopeDome Arduino Card 1.3 for Home Assistant

A Home Assistant integration for a ScopeDome dome with an Ethernet **Master** card and a paired **Slave** shutter card. It uses the local HTTP protocol described in the [official SDK](https://www.scopedome.com/wp-content/uploads/2020/10/ScopeDome_Arduino_Info_5.2SDK.pdf).

## Install with HACS

HACS must already be installed. If needed, follow the [official HACS installation guide](https://www.hacs.dev/docs/use/download/download/).

1. In Home Assistant, open **HACS → ⋮ → Custom repositories**. Enter `https://github.com/simplyr/ScopeDome-Arduino-HACS`, select **Integration**, and choose **Add**. See the [HACS custom repository instructions](https://www.hacs.dev/docs/faq/custom_repositories/).
2. Find **ScopeDome Arduino Card** in HACS, download the latest release, and restart Home Assistant.
3. Open **Settings → Devices & services → Add integration → ScopeDome Arduino Card**. Enter the local IPv4 address of the **Master** card, its HTTP port (usually `80`), and its HTTP password. The username is fixed to `scopedome` according to the [manufacturer's manual](https://www.scopedome.com/wp-content/uploads/2020/10/ScopeDome_Arduino_Card_Manual_EN.pdf). No `configuration.yaml` entry is needed.
4. Open the integration's **Configure** menu. Verify the shutter open and closed limit input values in two known physical shutter positions using the ScopeDome driver's **Shutters** and **Sensors** tabs. Enter the active input value (`0` or `1`) only after checking both switches. Until then, Open/Close controls and the interpreted shutter position remain unavailable or unknown.
5. Verify the dome Home switch input in the driver at Home and away from Home, then enter its active value. Set **Dome rotation angle** on the Home Assistant device page before using the left/right buttons. This input accepts 0–10 degrees in steps of 0.1°; `0` disables rotation. Changing the input does not move the dome. The value is restored after a Home Assistant restart. **Encoder pulses for 360°** are read automatically from the card using `getCalibratedRotation`. The step cannot exceed 10° of a full turn.
6. The second Configure screen accepts optional azimuth and Cloud Index calibration. Copy **Home Sensor Position** and the dome's Park angle from **Config → Dome**, and **Cloud Index** from **Config → Weather** in the ScopeDome driver. Also enter the **raw encoder count at Home** and whether the *raw count* increases during CW or CCW movement. Leave **Encoder pulses for 360° (manual fallback)** blank when the card has a valid calibration. If the command is unavailable or returns `0`, use **Encoder value for 360** from **Config → Card → Card configuration** as the fallback. Leave uncertain fields blank or `unknown`; no azimuth or Park state is estimated without all required values. The driver may display an encoder count with a different zero or sign from the raw card value.

The [ScopeDome driver manual](https://www.scopedome.com/wp-content/uploads/2021/02/ScopeDome-Driver-Manual-5.5.5.19-ENG.pdf) explains these calibration fields. Its optional `Arduino_Test_App.exe` utility is installed with the Windows driver in `Driver_LS`; it is not required for setup. Restart Home Assistant after a HACS update changes the Python files.

## Controls and states

- **Dome rotation angle** selects the relative movement in degrees. For example, choose `9` then press **Rotate dome left** for 9° left, or choose `1` then press **Rotate dome right** for 1° right. The integration converts the angle to the nearest representable encoder step and sends `moveDome=CW:<pulses>` or `moveDome=CCW:<pulses>`; the card stops automatically at the requested step. A valid card calibration or manual fallback is required. If the dome is already moving, the integration sends Stop first and waits up to five seconds for the motor relays to report stopped before issuing the new step. It rechecks safety alarms after the stop. The card retains its configured direction-change delay. **Stop dome rotation** cancels a pending rotation request and stops the dome. Older pulse-based settings are converted to degrees on the first upgrade; `0` remains disabled.
- **Find home** sends the manufacturer's native `findHome` command after checking live rotation status and confirming a stop if needed. It uses the Home switch configuration stored in the card and does not start encoder calibration. Use **Stop dome rotation** to stop the search.
- **Go to park** moves to the **Dome park azimuth** saved in Configure. **Dome target azimuth** accepts `0–360°`; enter a value and press **Go to azimuth** to move there. `360°` and `0°` both mean North. Editing the input does not move the dome, and its value is restored after restart. These two GoTo buttons require valid azimuth calibration and choose the shortest angular path, using a relative encoder move rounded to the nearest pulse. The longest planned path is 180°. If already moving, Stop is sent first and the target step is recalculated from the updated position after the motor relays report stopped. A target within half an encoder pulse of the current position sends no new movement. GoTo is unavailable until the required calibration and target are valid. **Stop dome rotation** cancels pending navigation and stops current movement. GoTo does not implement custom cable-wrap or forbidden-azimuth limits.
- **Shutter control** is the standard Home Assistant cover, which groups Open, Stop, and Close in one row. Until shutter contact polarity is configured, this row shows only the square Stop button. Opening and closing require a verified limit-switch polarity and a safe, fresh card status. Version 0.2.3 removes the separate duplicate shutter buttons from the entity registry; use the cover actions in any scripts or automations that previously referenced those buttons.
- **Shutter position** shows Open, Closed, Opening, Closing, Between end stops, or Conflicting limit switches when the contacts are verified. The two raw limit inputs remain under Diagnostics for troubleshooting.
- **Dome at home** uses the verified Home switch input. **Dome at park** is an inferred state: the dome must be stopped and its calibrated azimuth must be within 1° of the configured Park angle. It is not a separate hardware Park signal. **Telescope park switch input** is a different raw input and describes the telescope, not the dome.
- **Dome azimuth** displays decimal degrees to two decimal places. **Dome azimuth (DMS)** displays the same angle as degrees, minutes, and seconds, matching the driver format (for example, `279°33′20″` equals about `279.56°`). **Dome direction** and **Home azimuth** report values when their required calibration values are supplied. Compass directions use North, North-East, East, South-East, South, South-West, West, and North-West. **Dome raw encoder count** remains available under Diagnostics and is measured in pulses, not degrees.

**Encoder pulses per turn** shows the effective span and a `source` attribute: `card`, `manual_fallback`, or `unavailable`. The card value takes precedence over a manual value. It is read at startup and every five minutes. A detected calibration operation clears the cached span and triggers another read when it finishes. Manual movements are blocked during card calibration.

## Weather and heater readings

The paired card status exposes **dome and shutter motor temperatures**, **electronics temperatures**, **outside temperature**, **hygrometer temperature and relative humidity**, **pyrometer ambient temperature**, and **sky temperature**. It reads the hygrometer from the Dome card and the outside and pyrometer probes from the Shutter card. A missing Shutter reading is not replaced by a Dome reading. The integration shows **Observed cloud index** as sky temperature minus outside temperature, plus the optional **Cloud index threshold** copied from the driver. **Cloudy (card sensor)** uses the Shutter card's cloud check and becomes unknown when that card is offline. The raw Shutter cloud code remains available in Diagnostics. The unused Dome cloud code, cloud input, and rain input entities are removed in version 0.2.4. The Dome safety alarm remains available because the Master can monitor emergency conditions from the Slave. Missing or implausible probe readings show as unavailable rather than a plausible-looking temperature.

**Rain detected** reports interpreted rain status in Sensors. The official ScopeDome Cloud/Rain Sensor has an active LOW output: raw `0` means rain and raw `1` means dry ([card manual, page 22](https://www.scopedome.com/wp-content/uploads/2020/10/ScopeDome_Arduino_Card_Manual_EN_PlugAnd_Play_2.0.pdf)). This is the default from version 0.2.8, including existing installations. **Shutter rain input** keeps its raw meaning: On is `1`, Off is `0`; it is not an interpreted rain alert. Use **Rain detected** for dashboards and rain automations. Configure **Rain detected input** as `1` only for an inverted input or a different sensor. This option changes interpretation in Home Assistant and sends no card settings. Both entities report unknown when the Shutter card is offline; Rain detected also exposes `raw_input` and `active_level` attributes.

**Dome motor heater**, **Shutter motor heater**, and the two **electronics heaters** show the documented `REL_MOTOR` and `REL_INBOX` output states of each card. They report the controller's relay state, not measured heater current. Check the physical relay wiring if your installation has custom assignments. Weather data read only by an external station or a Windows driver log, such as wind speed, are not in the card's `getStatus` response and are not shown by this integration.

## Safety alarms and troubleshooting

**Dome safety alarm** and **Shutter safety alarm** reflect the controller's emergency flags. The **Dome alarm source** and **Shutter alarm source** sensors explain the codes defined in the SDK: `0` = no alarm, `1` = digital input, `2` = analog input, `3` = cloud sensor. They cannot identify the exact physical sensor or rule. A Master emergency can be configured to monitor a Slave input, so simultaneous alarms do not necessarily mean two separate failures. Shutter actions remain blocked while an alarm is active.

From version 0.2.8, a **cloud emergency (code 3) alone does not block manual dome rotation**. The manufacturer's weather emergency functions close the shutter ([driver manual, pages 23-24](https://www.scopedome.com/wp-content/uploads/2021/02/ScopeDome-Driver-Manual-5.5.5.19-ENG.pdf)). Cloud alarm indications remain visible, and the integration does not clear or reconfigure controller emergency rules. Dome rotation still requires fresh status, a connected Shutter card, valid encoder calibration, a selected angle, and no digital, analog, or unknown emergency codes. Home finding, calibration, and conflicting motor signals also block rotation. A rejected request is not sent to the card; a successful rotation with cloud code 3 no longer produces the previous action-error notification.

Starting with version 0.2.7, a blocked rotation or shutter action identifies the reported condition: **Shutter card is offline**, **Dome safety alarm**, or **Shutter safety alarm**. Alarm messages include the type and numeric code, and simultaneous conditions are listed together. These messages come from the integration's check of fresh card status before sending the movement command. In the device's Diagnostics section, check **Shutter card connected**, both safety alarms, and both alarm source sensors at the time of the failure. More precise messages do not clear an alarm or change the movement interlocks.

If an alarm appears intermittently, inspect the ScopeDome driver's **Sensors**, **Weather**, and **Internal Sensors** tabs and its card error log while the alarm is active. **Shutter rain input** appears under Sensors alongside Cloudy; the raw Shutter cloud input remains under Diagnostics. The optional Arduino Test App's **Get Status → Status Txt** can expose `MASTER_EMERGENCY`, `SLAVE_EMERGENCY`, and the input values; its **Emergency Shutter Close** tab shows the configured rule. Do not clear or disable an emergency trigger without finding its cause.

Setup sends only read commands: `getMode`, `getMac`, `getStatus`, and the optional `getCalibratedRotation`. Polling sends `getStatus`, with a calibration read every five minutes or after a detected card calibration. A failed optional read leaves status monitoring available and uses a valid manual fallback if configured. The integration never starts calibration or changes card settings. Movement commands are limited to documented bounded dome rotation, native Find Home, shutter open/close, and stop commands. Shutter movement requires a connected Slave card, no safety alarm, verified limit contacts, and no conflicting motor movement. Dome rotation uses the dedicated rotation checks described above. Keep the manufacturer's physical end stops, weather protection, and UPS rules configured independently of Home Assistant. Supervise the first movement from Home Assistant at the dome.

### Intermittent unavailable readings

All entities share one status update every 15 seconds. A failed update makes the device entities unavailable; the dashboard shows these readings as Unknown. Starting with version 0.2.5, a transient network failure or temporary HTTP server error during `getStatus` gets one additional read attempt after 0.5 seconds. Each request has an 8-second timeout. The retry delay releases the HTTP request lock so a Stop request can run. If both reads fail, the integration reports the failure and waits for the next scheduled update. It does not present old status as current or permit new movement using old status. Authentication failures, invalid protocol data, and permanent HTTP errors are not retried. Movement commands are never automatically repeated.

For persistent failures, inspect **Settings → System → Logs** for `scopedome_arduino`. Error messages distinguish a request timeout, the network exception type, and an HTTP status code without including credentials or the response body. A successful retry can reduce brief unavailable periods; it does not repair a network or controller fault.

### Movement acknowledgement errors

From version 0.2.9, movement acknowledgements can echo the command verb without its arguments: a request such as `moveDome=CW:9` accepts `moveDome|OK|...` as well as `moveDome=CW:9|OK|...` or the legacy bare `OK`. The echoed verb must match the sent command, and the status must be exactly `OK`. An acknowledgement for another verb, a different full request, malformed data, or an explicit error is rejected. Commands are never repeated automatically. An unrecognized response can arrive after movement has already started; use Stop before trying again. The change affects response parsing and does not alter movement limits or alarm handling.

The integration accepts the 12-group Master/Slave status format documented in SDK 5.2. Tests also cover a supplied firmware 7.2 status sample. If your response format differs, setup fails safely. Adapting the parser would require the firmware version and a redacted sample `getStatus` response.

Telescope tracking and automatic slaving are not implemented. HTTP Basic Auth does not use TLS here; connect only over a trusted local network or a protected VPN.

## Manual installation

Copy the entire `custom_components/scopedome_arduino` directory, including `translations`, to `<Home Assistant config>/custom_components/scopedome_arduino` and restart Home Assistant. Then follow steps 3–6 above. Use one installation method per Home Assistant instance so the source of future updates stays clear.

## Package checks

Run `python3 -m unittest discover -s tests -v` from the repository root. The mock tests make no network requests. This integration has not yet been tested against the physical controller or in a running Home Assistant instance.
